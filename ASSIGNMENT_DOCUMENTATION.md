### Question 1: Race Conditions
**Q**: Identify and explain TWO race conditions in the original code. For each:
- What shared resource is affected?
- Why is concurrent access a problem?
- What incorrect behavior could occur?

**Your Answer**:

The first race condtion happened on the shared counters like contextSwitchCount++. This is called a read-modify-write operation, when two threads read the same value before either writes back, an increment is lost, for example, P1 and P2 read counter=7, P1 increments it by one, P2 does the same, if P2 was the last to write, it would incorrectly compute counter=8, losing P1's increment. The second race condition involves executionLog which is an ArrayList, since arraylists are not thread safe, concurrent .add() calls can cause the ConcurrentModificationException during an internal array resize, which would lead to crashes or missing logs.

**Q**: Explain the difference between ReentrantLock and Semaphore. Where did you use each in your code and why?

**Your Answer**:

A ReentrantLock is a mutual exclusion tool which is used to protect data integrity by allowing only a single thread to access critcal sections at a time. I used it in SharedResources to protect the counters anf executionLog because
these variables are shared and they must stay consistent. However regarding semaphores, they manage resource permits, I still haven't implemented semaphores in my code but when i eventually do, I will use a binary semaphore in the process class to control access to the CPU. In short, Locks protect the state of data, semaphores manage the flow of execution.

### Question 4: Lock Granularity Design Decision 
**Q**: For Task 1 (protecting the three counters), explain your lock design choice:
- Did you use ONE lock for all three counters (coarse-grained) OR separate locks for each counter (fine-grained)?
- Explain WHY you made this choice
- What are the trade-offs between the two approaches?
- Given that the three counters are independent, which approach provides better concurrency and why?

**Your Answer**:

I used one lock (coarse-grained) for all of my counters to simplify the logic and keep it safe. Coarse-grained locking makes managing easier but it can cause bottlenecks. Fine-grained uses different locks which is a bit harder to implement but improves speed. Since these counters are independent, fine-grained locking provides better concurrency by allowing threads to modify different values at the same time. Personally chose the single lock because its easier to implement and guarantees consistency and avoids deadlocks.
